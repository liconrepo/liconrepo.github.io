The series so far has been about Claude Code. But many people who start with Claude are not writing software at all, and many developers use the chat apps more than they admit. This final part does two jobs. First, it covers the parts of Claude that are not Claude Code: the chat apps and how a non-developer can use Claude Code too. Second, it gives you a learning path: a first-week plan, practice exercises, the official courses and docs, a way to stay current, and a one-page quicksheet of everything in the series.

Part 8 in 60 seconds
  • The Claude apps (web, desktop, phone) are for conversation and everyday work. Claude Code is for working inside folders of files, and you do not need to be a programmer to use it.
  • The desktop app has three tabs: Chat, Cowork and Code.
  • A week of 20-minute steps is enough to build a solid foundation. The plan below links every step to a part of this series.
  • Anthropic publishes free courses, interactive lessons inside Claude Code (/powerup), release notes and a docs index. Use them to stay current.
  • This series is a snapshot from October 2026. When something differs, trust the official docs.

1. The Claude apps

Back in Part 1 I separated Claude (the models) from Claude Code (a coding assistant that works in your project). The consumer door to the same models is the Claude apps: claude.ai in a browser, the desktop app, and the mobile apps. You sign in with a Claude account and chat. Anthropic's Help Center has a short "Get started with Claude" collection that covers the basics, including where you can access Claude, what interfaces you can use, and what you can use Claude for.

3. Claude Code for people who do not code

This is the part most people miss. The official terminal guide for new users says plainly that you can use Claude Code even if you have never used a terminal, and that you do not need to know how to code: describe what you want in plain English and Claude writes the code for you. It also works in any folder, not only code. The docs say you can run it in a notes vault or a documentation folder to search, edit and reorganise content the same way you would code.

The docs suggest three starting ideas. Here are their own prompts:

IdeaExample prompt from the docs
Build something smallmake me a simple webpage that says hello world (then double-click the HTML file to open it in your browser)
Work with files you already havelook at the screenshots on my Desktop and rename them based on what's in each image
Ask questions and planI want to build a personal budget tracker. What would I need?
A gentle way to start without a terminal
  1. Download the desktop app, sign in, and open the Code tab.
  2. Pick a small folder you can afford to experiment in (a copy of important files, not the originals: my advice).
  3. Start with a question, not a change: explain what is in this folder.
  4. Stay in Manual mode. When Claude asks before creating or changing files, read the prompt and choose Yes (in the terminal, pressing Enter chooses Yes).
  5. Look at the result, then ask for the next small step.

Everything in Parts 1 to 3 still applies: the safety checklist, plan mode for anything big, and a short CLAUDE.md file to tell Claude how you like things done. For a non-developer, the CLAUDE.md might say who you are, what this folder is for, and how you want results formatted, rather than build commands.

5. Your first week: a day-by-day plan

This plan is my own suggestion, not an official curriculum. It uses short sessions that build on each other, and every day links to the part of the series that explains it. Aim for 20 to 40 minutes a day on a small project you know well.

DayDoDone when…Read
1Install, sign in, open a small project. Ask five questions: what it does, how to run it, where the main entry point is, what technologies it uses, how the folders are organised.You can explain the project to a friend using only Claude's answers, and you know how to interrupt and quit.Part 1
2Switch to plan mode. Ask for a plan for a small change. Edit the plan with Ctrl+G, approve it, and ask for tests to be run.The change works and a test or check proved it.Part 5, sections 2 to 5
3Run /init, then trim the result to what Claude would get wrong without it. Run /context to confirm it loaded.CLAUDE.md is short (the docs' ceiling is about 200 lines) and every line is specific.Part 2
4On a new branch, ask Claude to make a change, commit it, and write a pull request description. Read git diff first.You reviewed the diff and the PR text before sending anything.Part 5, section 7
5Run /usage after a long chat, then /clear, redo a small task, and compare. Try the same task on a smaller model.You can say roughly what a session cost and what changed the number.Part 3, section 2
6Add one extension: a skill for something you repeat, one MCP server you trust, or a read-only subagent for review.You used it once and can say what it saved.Part 6
7Review the week. Delete stale CLAUDE.md lines. Ask Claude to write a handoff note for the next session and start a fresh session from it.The new session picks up where you stopped without you retelling the story.Part 3, section 4

After week one: add automation only when you have a repeatable job (Part 7), and bring teammates in with a shared baseline of committed files rather than telling everyone to copy your setup.

6. Ten practice exercises

Learning sticks when you do things. These are my own exercises, written around prompts the official docs recommend. Do them on a throwaway branch or a practice project.

#ExerciseSkill practised
1Ask for an overview, then trace how one feature works from the UI to storage, using the prompts in Part 5.Reading a codebase
2Introduce a small bug on purpose. Describe only the symptom and the likely location, and ask Claude to write a failing test first, then fix it.Symptom-based prompts, verification
3Pick a function and ask for a refactor that keeps behaviour the same, then have it run the tests.Small, verified increments
4Ask Claude to find untested functions, add tests, and run them.Test-driven helpers
5Use the interview prompt to turn a vague idea into a SPEC.md, then build it in a fresh session.Specs and clean context
6Make Claude go wrong on purpose (a vague prompt), correct it twice, then use /clear and restate it. Compare.Knowing when to start clean
7Create a read-only reviewer subagent and ask it to review your last diff against your plan.Subagents, independent review
8Run one task on two different models and compare quality, time and the /usage figure.Model choice and cost
9Write a three-line CLAUDE.md rule for a mistake Claude keeps making, and see if the mistake stops.Turning corrections into memory
10Write a one-line script around claude -p that summarises git log or explains a log file, then ask for JSON output and parse it with jq.Non-interactive mode

8. Staying current

Claude Code, the models and the docs all change quickly. A few habits keep you from being surprised:

  • Keep Claude Code updated. Native installs update themselves in the background; Homebrew, WinGet and Linux package installs do not, so run the upgrade command from Part 1 or claude update. claude --version shows what you have.
  • Read the release notes. The Help Center keeps a release notes article for the apps.
  • Check model status before you pin one. The deprecations page shows retirement dates (Part 4). Anthropic says it gives at least 60 days' notice for publicly released models.
  • Prefer the docs index to memory. The docs publish an index at code.claude.com/docs/llms.txt, which you can also hand to Claude: ask it to read the current docs before answering.
  • Re-audit your own setup now and then. Run /doctor, prune CLAUDE.md, and delete plugins you no longer use.
  • Remember this series is a dated snapshot. Every figure and command here was checked against the official pages in October 2026. When your version behaves differently, believe the docs.

Ten rules to remember

  1. The context window is the scarce resource. Keep it clean.
  2. Claude does not learn from your usage. Your notes do.
  3. Explore and plan before you implement, unless the change is one sentence.
  4. Give Claude a check it can run, and ask for evidence.
  5. Work on a branch and read the diff.
  6. Stay in Manual mode until you trust the task.
  7. Keep secrets out of reach, and treat untrusted content as hostile.
  8. Correct early; after two failed corrections, /clear.
  9. Prune CLAUDE.md, skills, plugins and permissions regularly.
  10. When in doubt, check the official docs.
