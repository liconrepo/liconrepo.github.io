1. What is a design pattern?

A design pattern is a named, proven answer to a problem that keeps appearing in code. It is not a library you import. It is a shape you recognize and reuse, and the name is the real gift: “put a proxy in front of it” replaces a ten-minute explanation.

Think of recipes. “Fold the egg whites into the batter” is a technique with a name. Cooks do not reinvent it each time. Patterns are the named techniques of programming.

Where this article comes from. It is inspired mainly by Wikipedia’s Software design pattern page and follows its catalogue of Creational, Structural, Behavioral and Concurrency patterns. Of the 58 patterns listed there, this article covers 53 (about 91%). The names and families are Wikipedia’s; the explanations, Kotlin code, diagrams and exercises are my own. I left out five that do not translate to Kotlin or Android: Twin (a workaround for languages without multiple inheritance), Front controller and Service handler (server-side web and network servers), Compute kernel (GPU programming) and Safe Concurrency with Exclusive Ownership of Objects (a niche research pattern).

2. Creational patterns

How objects get made. These patterns hide the details of creation so the rest of the code does not depend on concrete classes.

Abstract factory ★ Popular

A factory of factories: one interface that creates a whole family of related objects, so you can swap the entire family (light theme widgets, dark theme widgets) at once.

The idea in Kotlin (a complete program you can run)

interface Button { fun render(): String }
interface Checkbox { fun render(): String }
interface WidgetFactory { fun button(): Button; fun checkbox(): Checkbox }

class LightButton : Button { override fun render() = "[ light button ]" }
class LightCheckbox : Checkbox { override fun render() = "[ ] light checkbox" }
class DarkButton : Button { override fun render() = "[ dark button ]" }
class DarkCheckbox : Checkbox { override fun render() = "[x] dark checkbox" }

class LightFactory : WidgetFactory {
    override fun button() = LightButton()
    override fun checkbox() = LightCheckbox()
}
class DarkFactory : WidgetFactory {
    override fun button() = DarkButton()
    override fun checkbox() = DarkCheckbox()
}

fun screen(factory: WidgetFactory) = println(factory.button().render() + "  " + factory.checkbox().render())

fun main() {
    screen(LightFactory())
    screen(DarkFactory())      // the whole family changes together
}
Linked to SOLID

O: Open/Closed · D: Dependency Inversion

New families are added as new factories (O) and screens depend only on the factory interface (D).

In Android and Kotlin: Theme or platform kits, a DataSourceFactory that returns matching local and remote classes for each build flavor.

Builder ★ Popular

Build a complex object step by step, then validate and produce it in one go. Kotlin gives you named arguments, default values and lambda-with-receiver DSLs.

The idea in Kotlin

data class Request(val url: String, val method: String, val headers: Map<String, String>)

class RequestBuilder {
    var url = ""
    var method = "GET"
    private val headers = mutableMapOf<String, String>()
    fun header(key: String, value: String) { headers[key] = value }
    fun build(): Request {
        require(url.isNotBlank()) { "url is required" }
        return Request(url, method, headers.toMap())
    }
}
fun request(init: RequestBuilder.() -> Unit) = RequestBuilder().apply(init).build()

val r = request { url = "https://example.com"; header("Accept", "application/json") }
Linked to SOLID

S: Single Responsibility

Construction rules live in the builder, not scattered across callers: Single Responsibility (S). The finished object stays immutable.

In Android and Kotlin: Retrofit.Builder(), AlertDialog.Builder, NotificationCompat.Builder, Room.databaseBuilder.

Dependency injection ★ Popular

A class does not create what it needs. Its dependencies are handed in from outside, usually through the constructor, so you can give it real or fake ones.

The idea in Kotlin

interface Clock { fun now(): Long }
interface Sink { fun write(line: String) }

class ReportService(private val clock: Clock, private val sink: Sink) {
    fun publish(title: String) = sink.write("$title @ ${clock.now()}")
}

object SystemClock : Clock { override fun now() = System.currentTimeMillis() }
object ConsoleSink : Sink { override fun write(line: String) = println(line) }

fun main() {
    ReportService(SystemClock, ConsoleSink).publish("Daily")   // wired once, at the edge
}
Linked to SOLID

D: Dependency Inversion

This is Dependency Inversion (D) made practical: depend on Clock and Sink interfaces, receive the real ones at the edge of the app.

In Android and Kotlin: Hilt, Dagger, Koin. The architecture series covers them in Part 6.

Factory ★ Popular

One place decides which class to create, so the rest of the code only knows the interface.

The idea in Kotlin

interface Notifier { fun send(message: String): String }
class EmailNotifier : Notifier { override fun send(message: String) = "email:$message" }
class SmsNotifier   : Notifier { override fun send(message: String) = "sms:$message" }

object NotifierFactory {
    fun create(kind: String): Notifier = when (kind) {
        "email" -> EmailNotifier()
        "sms"   -> SmsNotifier()
        else    -> throw IllegalArgumentException("unknown kind: $kind")
    }
}
Linked to SOLID

O: Open/Closed · D: Dependency Inversion

The client depends on the Notifier interface (D), and adding a new kind touches only the factory (O at the construction point).

In Android and Kotlin: ViewModelProvider.Factory, Fragment factories, creating the right repository for a build flavor.

Lazy initialization ★ Popular

Delay creating something expensive until the first time it is really needed, then remember it.

The idea in Kotlin (a complete program you can run)

class Heavy {
    init { println("Heavy created") }
    fun hello() = "hello"
}

class Screen {
    val heavy by lazy { Heavy() }      // not created yet
}

fun main() {
    val screen = Screen()
    println("screen created")
    println(screen.heavy.hello())      // created here, on first use
    println(screen.heavy.hello())      // reused
}
Linked to SOLID

S: Single Responsibility · D: Dependency Inversion

Expensive setup lives behind the property (S); callers just use the value.

In Android and Kotlin: Kotlin has it built in: by lazy { }, plus lateinit var for values set later.

Multiton

Like Singleton, but one instance per key: a map of named, shared instances.

The idea in Kotlin (a complete program you can run)

class Logger private constructor(val name: String) {
    companion object {
        private val instances = mutableMapOf<String, Logger>()
        fun of(name: String): Logger = instances.getOrPut(name) { Logger(name) }
    }
    fun log(message: String) = println("[$name] $message")
}

fun main() {
    Logger.of("net").log("connected")
    println(Logger.of("net") === Logger.of("net"))   // true: same key, same instance
    println(Logger.of("net") === Logger.of("db"))    // false: different key
}

Object pool

Keep a set of ready-made, reusable objects and lend them out, instead of creating and destroying them again and again.

The idea in Kotlin (a complete program you can run)

class Pool<T>(size: Int, create: () -> T) {
    private val free = ArrayDeque<T>().apply { repeat(size) { addLast(create()) } }

    fun <R> use(block: (T) -> R): R {
        val item = free.removeFirstOrNull() ?: error("pool exhausted")
        try {
            return block(item)
        } finally {
            free.addLast(item)         // always give it back
        }
    }
}

fun main() {
    var created = 0
    val pool = Pool(2) { created++; StringBuilder() }
    repeat(5) { i ->
        pool.use { sb ->
            sb.setLength(0)
            sb.append("job ").append(i)
            println(sb)
        }
    }
    println("objects created: $created")   // 2, not 5
}
Linked to SOLID

S: Single Responsibility · D: Dependency Inversion

The pool owns reuse (S); users borrow through a small interface.

In Android and Kotlin: RecyclerView view holders and its RecycledViewPool, bitmap pools in image loaders, database connection pools, Message.obtain().

3. Structural patterns

How objects are put together. These patterns combine classes and objects into larger structures while keeping them flexible.

Adapter ★ Popular

Make an object with the wrong interface fit the interface you need, by wrapping it. Also called Wrapper or Translator.

The idea in Kotlin

interface Thermometer { fun celsius(): Double }
class LegacySensor(private val fahrenheit: Double) { fun readFahrenheit() = fahrenheit }

class SensorAdapter(private val legacy: LegacySensor) : Thermometer {
    override fun celsius() = (legacy.readFahrenheit() - 32) * 5 / 9
}
Linked to SOLID

D: Dependency Inversion · O: Open/Closed

Your code depends on Thermometer (D); the old sensor is reused without being edited (O).

In Android and Kotlin: RecyclerView.Adapter, mappers from API DTOs to domain models, wrapping a third-party SDK.

                instance ?: Config().also { instance = it }   // 2nd check inside the lock
            }
    }
}

fun main() {
    println(Config.get() === Config.get())     // true
    // In real code, prefer:  val config by lazy { Config() }
}
Linked to SOLID

S: Single Responsibility

Thread-safe creation is isolated in one place (S).

In Android and Kotlin: Kotlin hides it: by lazy uses it internally. Write it yourself only to learn why @Volatile matters.

Event-based asynchronous

Start work in the background and get notified by an event (callback) when it finishes or fails, instead of waiting for it.

The idea in Kotlin (a complete program you can run)

}

Guarded suspension

A thread waits until a condition is true (a message has arrived) before it continues.

The idea in Kotlin (a complete program you can run)

import java.util.concurrent.locks.ReentrantLock
import kotlin.concurrent.thread
import kotlin.concurrent.withLock

class Mailbox {
    private val lock = ReentrantLock()
    private val hasMessage = lock.newCondition()
    private var message: String? = null

    fun put(m: String) = lock.withLock {
        message = m
        hasMessage.signalAll()
    }

    fun take(): String = lock.withLock {
        while (message == null) hasMessage.await()     // the guard: wait until it is true
        message!!.also { message = null }
    }
}

fun main() {
    val box = Mailbox()
    val reader = thread { println("got: ${box.take()}") }
    Thread.sleep(50)                                   // the reader is waiting
    box.put("hello")
    reader.join()
}
Linked to SOLID

S: Single Responsibility

Waiting rules are encapsulated in the mailbox (S).

In Android and Kotlin: BlockingQueue.take(), CountDownLatch, a coroutine channel.receive() (suspends instead of blocking).

Join

Wait until several concurrent tasks have all finished before continuing.

The idea in Kotlin (a complete program you can run)

import kotlin.concurrent.thread

fun main() {
    val results = java.util.Collections.synchronizedList(mutableListOf<Int>())

        thread {
            Thread.sleep(10L * n)             // different durations

Messaging design pattern (MDP)

Components communicate by sending messages into a queue instead of calling each other directly or sharing memory.

The idea in Kotlin (a complete program you can run)

import java.util.concurrent.LinkedBlockingQueue
import kotlin.concurrent.thread

sealed interface Msg
data class Greet(val name: String) : Msg
object Stop : Msg

fun main() {
    val inbox = LinkedBlockingQueue<Msg>()

    val consumer = thread {
        while (true) {
            val msg = inbox.take()               // waits for the next message
            if (msg is Greet) println("hello ${msg.name}") else break
        }
    }

    inbox.put(Greet("Ana"))
    inbox.put(Greet("Ben"))
    inbox.put(Stop)
    consumer.join()
}

Producers and consumers are decoupled (D); new message types are added without editing the sender (O).

In Android and Kotlin: Handler/Looper, Channel, BlockingQueue, WorkManager, Kafka and other brokers on the backend.

Monitor object

An object whose methods are all mutually exclusive, so only one thread is inside it at a time. The object guards its own state.

The idea in Kotlin (a complete program you can run)

import kotlin.concurrent.thread

class BoundedCounter(private val max: Int) {
    private var value = 0

    @Synchronized fun increment(): Boolean {
        if (value >= max) return false
        value++
        return true
    }
    @Synchronized fun current() = value
}

fun main() {
    val counter = BoundedCounter(5)
    val threads = List(4) { thread { repeat(10) { counter.increment() } } }
    threads.forEach { it.join() }
    println(counter.current())            // exactly 5, never more
}

Reactor

One event loop waits for events and dispatches each to the handler registered for it.

The idea in Kotlin (a complete program you can run)

class Reactor {
    private val handlers = mutableMapOf<String, (String) -> Unit>()
    private val events = ArrayDeque<Pair<String, String>>()

    fun register(type: String, handler: (String) -> Unit) { handlers[type] = handler }
    fun post(type: String, payload: String) { events.addLast(type to payload) }

    fun run() {
        while (events.isNotEmpty()) {
            val (type, payload) = events.removeFirst()
            val handler = handlers[type]
            if (handler != null) handler(payload) else println("no handler for $type")
        }
    }
}

fun main() {
    val reactor = Reactor()
    reactor.register("click") { println("clicked $it") }
    reactor.register("key") { println("key $it") }
    reactor.post("click", "OK")
    reactor.post("key", "A")
    reactor.post("scroll", "10")
    reactor.run()
}
Linked to SOLID

O: Open/Closed · D: Dependency Inversion

Handlers register for event types without the loop knowing them (O, D).

In Android and Kotlin: The Android main thread’s Looper + Handler, Netty and other event-loop servers, Node.js.

Read-write lock

Many threads may read at the same time, but a writer needs exclusive access. Faster than one plain lock when reads dominate.

The idea in Kotlin (a complete program you can run)

import java.util.concurrent.locks.ReentrantReadWriteLock
import kotlin.concurrent.read
import kotlin.concurrent.write

class Cache {
    private val lock = ReentrantReadWriteLock()
    private val map = mutableMapOf<String, String>()

    fun get(key: String): String? = lock.read { map[key] }          // many readers allowed
    fun put(key: String, value: String) { lock.write { map[key] = value } }   // exclusive
}

fun main() {
    val cache = Cache()
    cache.put("lang", "Kotlin")
    println(cache.get("lang"))
}

7. When not to use a pattern

  • Patterns solve pain, not boredom. If nothing hurts, the plain code is the right code (KISS).
  • Wait for the second case. One payment method needs no Strategy. A second one is the signal.
  • Kotlin already has many. object is a Singleton, by lazy is Lazy initialization, by is Delegation, copy() is Prototype, use { } is RAII, extension functions replace many wrappers, sealed + when replaces Visitor, and lambdas replace many one-method Strategy and Command classes.
  • Do not name-drop. Class names like OrderFactoryManagerImpl hide the idea. Name things by what they do.
  • Be wary of global state. Singleton and Multiton need a reset() in tests only because shared state leaks between them.
  • Prefer high-level tools for concurrency. Learn the concurrency patterns to understand what coroutines, Flow and executors do for you, then use those.
